# طراحی محصول و تجربهٔ کاربری

## هدف و شخصیت بصری

کنسول برای تیم عملیات است: پیدا کردن دستگاه، فهمیدن علت آماده‌نبودن، شروع جلسه و پایان امن آن. رنگ سبز برای وضعیت آماده، کهربایی برای نیاز به اقدام و خاکستری برای خاموش است؛ متن وضعیت همیشه کنار رنگ قرار دارد. سمت راست نوار ناوبری تیره، محتوای روشن و یک ردیف ۱۰ جایگاه قابل شمارش، شخصیت بصری پنل را می‌سازند. فونت Vazirmatn محلی، RTL و اعداد فارسی؛ شناسه، IP و شماره LTR هستند.

## نقشهٔ صفحات

| صفحه | تصمیم اصلی کاربر | اجزای اصلی |
|---|---|---|
| دستگاه‌ها | کدام دستگاه و آیا آماده است؟ | ظرفیت، ۴ شاخص، جست‌وجو، فیلتر، کارت/جدول، صفحه‌بندی |
| جزئیات دستگاه | شروع، کنترل یا رفع خطا؟ | وضعیت، CPU/RAM، پراکسی، داده، پشتیبان، تب کنترل و audit |
| جلسات و صف | چه کسی ظرفیت را مصرف می‌کند؟ | جلسات فعال، صف FIFO، لغو انتظار و پایان جلسه |
| شبکه و پراکسی | علت ارتباط ناموفق چیست؟ | ارتباط یک‌به‌یک، کشور، تأخیر، آزمون و وضعیت |
| پشتیبان‌ها | آیا نسخهٔ قابل اتکا دارم؟ | تاریخچه، verify، manifest، راه بازیابی |

معماری و راهنما در UI فعلی برای تحویل طراحی در دسترس‌اند؛ در نسخهٔ production می‌توان آن‌ها را فقط برای مدیر نمایش داد. هیچ بخش چت/AI تعریف نشده است.

## جریان‌های اصلی

### شروع جلسه

جست‌وجو با شناسه/alias/شماره → مشاهدهٔ وضعیت → روشن‌کردن → starting → بررسی سلامت → ready → کنترل. دکمهٔ start دوباره ارسال نمی‌شود و job ID در محصول متصل حفظ می‌شود. پر بودن ظرفیت خطای ترسناک نیست: «در صف؛ با آزادشدن جایگاه شروع می‌شود» و گزینهٔ لغو. شمارهٔ جایگاه صف بر اساس زمان درخواست است؛ زمان تخمینی ساختگی نمایش داده نشود.

### کنترل دستگاه

جزئیات → تب کنترل → مجوز همان Device → نمایش stream. آفلاین: توضیح و روشن‌کردن؛ booting: مراحل و امکان انصراف؛ ready: صفحهٔ واقعی، کلیدهای Home/Back، fit-to-screen و پایان جلسه؛ قطع stream: وضعیت روشن دستگاه حفظ و گزینهٔ اتصال دوباره. نمایش APK/شماره/OTP نباید خودکار ضبط یا در audit ذخیره شود. تصویر mock به‌عنوان live نشان داده نشود؛ نسخهٔ فعلی عمداً محل stream را با توضیح عدم اتصال نمایش می‌دهد.

### پایان جلسه

تأیید با نام Device و توضیح «داده حفظ می‌شود» → بستن کنترل → stopping → تأیید خاموشی → آزادشدن جایگاه. اگر صفحه بسته شد یا مرورگر offline شد، سرور طبق lease رفتار می‌کند؛ بسته‌شدن تب به‌تنهایی اثبات پایان جلسه نیست.

### افزودن دستگاه

فاز production: alias → شمارهٔ معتبر و یکتا → انتخاب proxy تخصیص‌نیافته → تست credential و IP → مرور خلاصه → provisioning. شناسه، volume و serial توسط سیستم تولید می‌شوند؛ فرم فنی از اپراتور شمارهٔ پورت نمی‌خواهد. خطای تکراری زیر فیلد با لینک دستگاه مجاز موجود؛ خطای مجوز نباید شمارهٔ دستگاه غیرمجاز را افشا کند. نمونهٔ فعلی فقط alias/شمارهٔ آزمایشی می‌گیرد و اتصال proxy را شبیه‌سازی می‌کند.

### بکاپ و بازیابی

بکاپ روی stopped فعال است؛ روی ready دکمه غیرفعال و توضیح پایان جلسه دیده شود. نتیجه شامل verify، storage و زمان است. بازیابی production: انتخاب نسخه → verify → نمایش identity/digest → تایپ Device ID → بازیابی volume جدید → آزمون → فعال‌سازی. خطر جایگزینی داده با یک دکمهٔ ساده مخفی نشود. نسخهٔ فعلی رکورد نمایشی دارد و دانلود/restore واقعی ندارد.

## حالت‌های خطا و دسترس‌پذیری

* loading: skeleton یا پیام کوتاه، بدون اعداد جعلی؛ درخواست قبلی در refresh دوباره اجرا نشود.
* empty: دلیل و اقدام مرتبط؛ جست‌وجوی خالی دکمهٔ پاک‌کردن فیلتر دارد.
* error: علت قابل‌اقدام («اعتبارنامهٔ پراکسی رد شد») و retry محدود؛ stack trace به UI نیاید.
* stale: timestamp آخرین مشاهده، برچسب قطع ارتباط و قفل start تا resync.
* forbidden: نمایش وضعیت مجاز، نه دادهٔ مخفی؛ ۴۰۱ به ورود و ۴۰۳ به توضیح دسترسی.
* success: toast برای نتیجهٔ کوتاه و audit برای اثر پایدار؛ toast تنها محل اعلام خطای مهم نباشد.
* keyboard: button واقعی، focus visible، dialog با focus trap و Escape، بازگشت focus به کنترل قبلی.
* responsive: در موبایل منوی کشویی، کارت تک‌ستونی، جدول با scroll افقی در container؛ صفحه نباید افقی scroll شود.
* ترجیح reduced motion رعایت شود. رنگ تنها نشانگر وضعیت نیست. در پذیرش production contrast و بزرگ‌نمایی ۲۰۰٪ بررسی شوند؛ ادعای انطباق کامل WCAG بدون audit نداریم.

## وضعیت پیاده‌سازی UI

اکنون کار می‌کند: ناوبری هفت صفحه، جست‌وجو، فیلتر، کارت/جدول، صفحه‌بندی، جزئیات، modal افزودن، validation شماره، شروع/توقف آزمایشی، سقف۱۰، صف FIFO، لغو، بکاپ نمایشی، رویدادها، تست پراکسی نمایشی و بازنشانی.

طراحی‌شده ولی هنوز متصل نیست: ورود/OIDC، کاربران واقعی و RBAC، فرم credentials تولیدی، API/SSE، stream، بازگردانی backup، پایگاه داده و audit پایدار. عنوان «مدیر عملیات» در UI نقش نمونه است و هیچ مجوز واقعی ایجاد نمی‌کند.

دادهٔ شبیه‌ساز فقط در memory همان tab است. refresh آن را بازنشانی می‌کند. ذخیره در localStorage یا خروجی CSV شماره‌ها انجام نمی‌شود. فرم عمداً درخواست شمارهٔ آزمایشی دارد. پس از اتصال production هیچ‌گاه خطای API با fallback به دادهٔ نمونه پوشانده نشود.

## سناریوهای پذیرش

۱. پیدا کردن num07، روشن‌کردن و مشاهدهٔ انتقال به ready؛ مصرف یک جایگاه.
۲. ثبت چهار start با هفت جایگاه اولیه؛ سه دستگاه شروع و چهارمی queued شود.
۳. پایان یک جلسه؛ queue اول به FIFO شروع شود و هیچ‌گاه ۱۱ slot مصرف نشود.
۴. start تکراری، back/forward مرورگر و بازشدن جزئیات job جدید نسازند.
۵. Device دارای proxy خراب شروع نشود؛ آزمون نمونه نتیجه را تغییر دهد و audit ثبت کند.
۶. شماره تکراری رد شود؛ دستگاه جدید num71 خاموش ایجاد شود.
۷. بکاپ دستگاه روشن رد/غیرفعال، برای خاموش رکورد ایجاد شود و identity ثابت بماند.
۸. بدون دادهٔ واقعی، mobile/keyboard/dialog و null result بررسی شوند.

این سناریوها تست UX نمونه هستند؛ تست integration سرور در سند معماری جدا تعریف شده است.
